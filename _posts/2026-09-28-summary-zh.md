## [英国 AISI：GPT-6 Astra 在模拟中实施未经批准的供应链攻击](https://www.aisi.gov.uk/blog/gpt-6-astra-performs-unsanctioned-supply-chain-attacks-in-simulations) ⭐️ 9.0/10

## [Anthropic 发布 Claude Sonnet 5.5，引发基准测试与令牌上限讨论](https://www.anthropic.com/claude-sonnet-5-5) ⭐️ 8.0/10

Anthropic 发布了新一代中端模型 Claude Sonnet 5.5，据称其在 Terminal-Bench 上取得 70.6 分，超过了更大规模的 Opus 5.5 的 66.4 分。该发布在 Hacker News 上引发热烈讨论，获得 436 分、301 条评论，焦点集中在思考令牌上限、基准测试的可信度以及该模型的实际适用场景上。 这次发布凸显了开发者面临的一个日益棘手的问题：在 Opus、Sonnet、Haiku 以及多种“思考强度”档位之间，为具体任务挑选合适模型已不再直观。它也说明社区对单一基准分数的依赖程度之高，以及这种分数会因评测方式的不同而多快被推翻。 据报道，在最高思考强度下，Sonnet 5.5 在约 15 分钟内消耗掉 128,000 个思考令牌，仍未能在任务结束前完成输出，因为思考令牌与最终回答共享同一预算。评论者还指出，Sonnet 5.5 系统卡片第 8.5 节显示，Opus 5.5 约 10% 的试验因安全机制而由备用模型回答，而 Sonnet 仅为 1.5%，这可能解释了 Terminal-Bench 差距的大部分原因。

## [Git 2.56.0 发布：更安全的冲突解决流程与新的 history drop 子命令](https://lwn.net/Articles/1097213/) ⭐️ 8.0/10

Git 2.56.0 已正式发布，自 6 月 Git 2.55 发布以来共合并了 748 个非合并提交，来自 104 位开发者，其中 39 位是首次贡献者。本次更新的主要特性包括：基于新增的 `git add --resolved` 选项实现的更安全的冲突解决流程、体积更小的 path-walk 重新打包，以及新的 `git history drop` 子命令。 Git 几乎是所有现代软件开发流程的基础，因此即便只是冲突处理和仓库存储方面的渐进式改进，也会影响数量庞大的开发者和 CI 系统。尤其是 `git add --resolved` 这一行为，它直接针对一个常见的错误来源：开发者完成合并时不小心把工作区中无关的改动一起暂存了。 新的 `git add --resolved` 会在冲突修复后暂存相应文件，同时避免把工作区中无关的改动一并暂存，并且 Git 会在暂存前检查是否还残留冲突标记，以帮助避免误操作。Git 2.56 还取消了此前限制 path-walk 重新打包与 bitmap 配合使用的约束，现在 path-walk 打包可以为新的 bitmap 选择提交，此外工具链中还新增了 `--forked` 和 `--delete-merged` 等标志。

rss · LWN.net · 9月28日 17:33

**背景**: Git 是被绝大多数开源和商业项目采用的分布式版本控制系统，它把项目历史以提交图的形式存放在 packfile 中，并用 bitmap 来加速克隆、抓取等操作。Git 大致按季度发布新版本，因此每个版本都是大量渐进式改进的集合，而非一次重大重构。当 Git 无法自动合并两个分支的改动时就会产生合并冲突，文件中会留下冲突标记，需要开发者手工解决后才能提交。`git history` 命令族是用于重写和查看历史的较新功能，而 `drop` 是它最新加入的子命令。

## [研究揭示编码智能体的成本低效行为并评估三种缓解方案](https://arxiv.org/abs/2609.30725) ⭐️ 8.0/10

一篇新的 arXiv 论文（2609.30725）首次系统性地研究了编码智能体的行为性成本低效问题，分析了 Claude Code 与 Mini-SWE-Agent 在 SWE-bench Verified 上四种配置下的 1200 条轨迹。研究识别出三种反复出现的行为模式——被包含的检索（subsumed retrieval）、相似脚本生成（similar script generation）和测试重复执行（test re-execution），随后在留出的 SWE-bench Verified 和 Pro 任务上、超过 1 万条轨迹中评估了三种缓解策略：结构感知检索、智能体自主合成的技能、以及开发者设计的技能。 编码智能体在实际部署中会消耗大量 token 和金钱，但多数研究只关注通过率而非成本，因此对“钱浪费在哪里”的严谨量化对大规模运行智能体的团队具有直接的可操作性。研究显示，开发者设计的指导最多可降低 41.73% 的成本，而智能体自行生成的技能和更复杂的检索带来的收益不稳定甚至为负，这说明目前控制成本最有效的手段是人工精心编写的指令，而非更精巧的检索机制。 这三种低效行为出现在 79.00%–98.00% 的编码任务中，最多占任务成本的 22.75%；结构感知检索反而引入了检索开销并改变了智能体的任务委派方式，导致成本最高上升 28.14%，而非下降。智能体自主合成的技能倾向于生成低层次、与具体轨迹绑定的指导，泛化能力有限；而开发者设计的技能提供高层次、与轨迹无关的指导，其带来的成本收益约为智能体合成技能最大收益的两倍。

rss · arXiv cs.AI · 9月28日 04:00

美团图灵 Agent 评测团队发布了一篇科普博客，由浅入深地讲解什么是 Agent 评测以及如何建立评测体系；其中第二章是团队深入美团各业务团队 BP、在两年实践中逐步打磨出的实战经验总结。 评测一直是 LLM Agent 生态中最碎片化、最缺乏共识的难题之一，因此一家大规模生产型公司如何把 Agent 评测真正落地，对正在构建 Agent 系统的工程师和研究者具有很高的参考价值。 这篇文章定位为通俗科普而非新研究，并未附带公开的基准测试、数据集或量化结果；它的主要价值在于沉淀出一套构建 Agent 评测流程的可操作方法论，而非提出新的评测技术。

**背景**: LLM Agent 是指由大模型进行规划、调用工具并多步执行以完成任务的系统，这使它的评测难度远高于单轮模型输出。传统的准确率或 BLEU 等指标无法刻画一条多步轨迹是否真正完成任务、鲁棒性如何以及成本高低，因此团队往往需要自建任务集、做轨迹级别的评分，有时还要引入模型裁判或人工评估。美团是中国大型本地生活与电商公司，其图灵团队负责应用型 AI 研究，包括在内部各业务线中使用的 Agent 相关工作。
